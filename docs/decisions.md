# Decisions

Short records of why we chose a tool or a pattern. Newest first.
Read the related entry before you change a decision. Add an entry for each new decision.

## 2026-11-20: Longer time limit for the tests of the whole trainingsbuch app

- **Context:** `CI - Test` failed for version 4.0: ten tests of `trainingsbuch` ran longer than the default limit of 5 s. A run again passed. These tests render the whole app with the list of all 359 workouts. On a computer, the slowest test takes about 1.4 s. On the GitHub runners, it takes up to five times as long, and the time changes from run to run.
- **Decision:** The test files that render the whole app (`app-*.test.tsx`, `exercise-filter-dialog.test.tsx`, `ai-entry-dialog.test.tsx`) set `vi.setConfig({ testTimeout: 15_000 })`. The project owner agreed. The tests check the same things as before. Only the time limit changes, and only for these files. All other tests keep 5 s.
- **Rejected:** A smaller catalog in the tests: the tests would no longer check the real list. A higher limit in `vitest.config.ts` for all tests: the other tests do not need it.
- **Decision:** The tests of the whole app are in four files: `app-list`, `app-results`, `app-own` and `app-history`. Vitest runs files in parallel, but the tests of one file one after the other. With one file of 37 s, no run could be shorter than this file. After the split, the unit tests take 24.5 s instead of 40 s on a computer with 12 cores. The shared helpers are in `test-app.tsx`.

## 2026-11-19: Loads for men or for women (trainingsbuch)

- **Context:** The built-in workouts give each load, height and distance as a pair: "43/29 kg", "24/20 Zoll". The first value is for men, the second for women. The project owner wants to switch between them.
- **Decision:** A second switch "Männer | Frauen" next to "kg | lb" on a built-in workout. The texts then show one value: "43 kg" or "29 kg". The switch is for all built-in workouts, like "kg | lb". `showLine()` in `units.ts` does both: first the unit system, then the value of the pair.
- **Decision:** The data file keeps the choice in `loadsFor` (schema version 3). Then it is the same on all devices.
- **Decision:** Own workouts can have values for women too, for example the "Box Jump Barbell Chipper" with 52.5/35 kg and 30/24 inches. Each part has `kgWomen` and `boxInchesWomen` (schema version 3). `null` means: the same for all. The form shows "Frauen (kg)" and "Box Frauen (Zoll)" next to the values for men, with "wie Männer" as the empty choice. A new box exercise starts with 24 inches for men and 20 for women. `partLine()` writes a pair in the form of the built-in workouts ("52,5/35 kg"), so `showLine()` picks the value for both kinds of workouts. An own workout shows the switch only if one of its parts has a value for women. The AI puts the second value of a pair ("24/20 in") into the field for women.
- **Decision:** The switch changes only the texts. For the results of the project owner, Rx stays the load for men (see "Record a result with the AI"). A user who does the loads for women saves "Scaled", or the app needs a later change.
- **Consequence:** Version 4.0 did not reach GitHub Pages (CI failed). Thus the box heights (schema version 2) and this switch (schema version 3) come together in version 4.0.

## 2026-11-19: Box heights always in inches (trainingsbuch)

- **Context:** In kg mode, `showUnits()` showed box heights in cm ("Box jumps, 61/51 cm"). Gyms give box heights in inches, also in countries with kg. Own workouts had no box height at all: "10 × Box Jump". The project owner wants the height always in inches and always next to a box exercise.
- **Decision:** In a line about a box (box jumps, box step-overs, step-ups), `showUnits()` shows a value in inches always in inches, in kg mode and in lb mode, with the German word: "24/20 Zoll". "in" next to German text reads like the German word "in". Other heights, for example of a pull-up bar, follow the unit system.
- **Decision:** Each part of an own workout has `boxInches` (schema version 2). The form shows "Box (Zoll)" for the exercises with a box (`hasBox()`: box jump, box jump-over, burpee box jump, burpee box jump-over, box step-over, step-up) and needs a value. It is a select with 12, 16, 20, 24 and 30 inches. On a phone, one tap sets it. A new part starts with 24, the Rx height for men in most workouts. The AI must give `boxInches` for a box exercise of a new workout. It takes the height from the input, or it asks the user. It does not guess.
- **Consequence:** The migration to version 2 sets `boxInches` to `null` in all parts: the old data has no height. A box exercise without a height shows "Boxhöhe fehlt", and the form asks for the height at the next change. `trainingsbuch` 4.0.
- **Not changed:** The built-in workouts "Drew" and "Wesley" show no box height. Their sources give none, and the catalog does not invent values.

## 2026-11-19: Photos with the camera of a phone (core, trainingsbuch)

- **Context:** With OneDrive, the apps work on a phone. In `trainingsbuch`, the user takes a photo of the whiteboard in the gym. On Android, the file dialog of "Foto" did not offer the camera. A camera photo has often 3 to 6 MB and 4000 pixels. `imageForAi()` refused images larger than 3.75 MiB.
- **Decision:** `CameraButton` in `packages/core` is a `FileButton` with `capture="environment"`: a tap opens the camera on the back. It shows only on a device with a touch screen as its main pointer (`(pointer: coarse)`). On a computer, the browser ignores `capture` and opens the file dialog, so a second button would only confuse. Next to it, "Foto wählen" opens the gallery or the files, with `accept="image/*"`.
- **Decision:** `imageForAi()` makes an image smaller before it reads it: at most 1568 pixels on the long edge, JPEG with quality 0.85. It does this also for formats that the AI does not read (for example HEIC), if the browser can read them. Claude makes larger images smaller itself, so the copy loses nothing for the AI. It saves mobile data, upload time and tokens. `createImageBitmap()` turns the photo by its EXIF orientation. The browser does the work (`OffscreenCanvas`), there is no new dependency.
- **Consequence:** `trainingsbuch` 3.1. `e2e/trainingsbuch.spec.ts` emulates a phone (`isMobile`, `hasTouch`) and checks that a photo of 4000 × 3000 pixels reaches the AI as 1568 × 1176 pixels.

## 2026-11-19: OneDrive as a second storage for the data (core)

- **Context:** The data folder works only in Chrome and Edge on a computer (File System Access API). The project owner wants to use the apps on a phone and in all browsers, for example `trainingsbuch` in the gym. The data must stay with the user, without a server of ours.
- **Decision:** On the first visit, the user picks the storage: "Wo sollen deine Daten liegen?". "Ordner auf diesem Computer" shows only in browsers with the folder dialog. "OneDrive" shows in all browsers. Its text says that the user sees the same data on all devices. The choice is for all apps of the web address, like the folder before. "Speicherort wechseln" opens the same choice. The data does not move to the new storage.
- **Decision:** OneDrive is one more `DataFolder` (`onedrive-folder.ts`). The store, the conflict check and the apps do not change. Later, Dropbox and Google Drive come in the same way, always in the folder `/Apps/Pocket Apps`.
- **Decision:** The app registration "Pocket Apps" in the Entra tenant of the project owner has the platform "SPA" and only the scope `Files.ReadWrite.AppFolder`: the apps see only `/Apps/Pocket Apps`, but in this folder all files, also the files of the OneDrive desktop program. The login is OAuth 2.0 with PKCE in the browser, without a secret and without a server. The tokens stay in IndexedDB, like the folder handle.
- **Decision:** The login always comes back to the start page of the site. The start page ends the login and goes back to the page of the app. Then the registration needs one address per web address (dev server, `pnpm serve`, GitHub Pages), and a new app needs no change of the registration.
- **Decision:** The Content Security Policy of each stateful app allows the Microsoft login, Microsoft Graph and the download servers of OneDrive (`STORAGE_ORIGINS`). `pocketApp.network` stays about the app itself: an app with `"network": false` can keep its data in OneDrive. The launcher card of such an app still shows "Nutzt keine Online-Dienste".
- **Consequence:** Microsoft gives a browser app a refresh token for 24 hours only. A new refresh token keeps the end time of the first one. Thus the user clicks "Anmelden" once a day, also with daily use. Microsoft usually remembers the account, so the user does not type the password again. If the login ends while an app is open, a save fails, and the change that is not saved is lost after the new login. The browser warns before the page leaves.
- **Consequence:** Each read and each save goes over the internet. The prototype measured 0.5–1 s per request: about 1 s to open an app and about 1.3 s for a save in the background. A read gets the time first and then the text. A save sends the eTag of the conflict check as `If-Match`. Thus a change on another device between the check and the write is never lost.
- **Consequence:** Without internet, an app with OneDrive cannot load or save. The store shows the error and tries again.
- **Rejected:** Google Drive first: a browser app gets no refresh token (one login click per hour), and the scope `drive.file` does not see the files of the desktop program. Dropbox: a good fit (long refresh tokens), it comes later. A server of our own: we would be responsible for the data of other people (GDPR), and we would run the server. A native app: costs for the App Store, and the data still needs a cloud for the sync.
- **Changes:** "Apps on GitHub Pages, data in a local folder (like draw.io)": the apps are no longer only for Chrome and Edge.

## 2026-11-19: AGENTS.md holds rules, the modules hold their API docs

- **Context:** `AGENTS.md` had grown to 460 lines. Each agent session loads all of it. About a third was API documentation: how to use `useAi()`, how the data file store works, how `useSubPage()` behaves. The same facts were also in the JSDoc. Two places for one fact can drift apart.
- **Decision:** `AGENTS.md` keeps the rules, the steps and the gotchas: what to do, what not to do, and why when it is not clear. For the details of a module, it points to the module.
- **Decision:** The two large modules have a `README.md` next to their code: `packages/core/src/data-file/README.md` and `packages/core/src/ai/README.md`. `AGENTS.md` says to read the README before you change a stateful app or an AI feature. Small modules keep their documentation in the JSDoc only (for example `useSubPage()` and `fetchJson()`).
- **Rejected:** One `docs/api.md` for all modules: it is far from the code, so a change of the code does not remind anyone to change it.

## 2026-11-19: Sub-pages in the browser history (core)

- **Context:** `trainingsbuch` (the detail of a workout) and `attraktor` (an attractor) show a sub-page after a click. A button leads back to the main page. The back button of the browser did not: it left the app, because the apps changed the page only in React state. AGENTS.md allows no router.
- **Decision:** `useSubPage()` in `packages/core/src/sub-page.ts`. It works like `useState` for one ID. `open(id)` adds an entry to the browser history (`history.pushState`) with the ID in the hash: `trainingsbuch.html#fran`. The event `popstate` sets the ID again. Thus the back and forward buttons of the browser, the back button of the mouse and Alt+Left work. The button in the app calls `back()`: it goes one step back in the browser history. Thus the button in the app and the back button of the browser do the same thing. `back()` shows the main page at once, before the browser goes back. Thus a fast second click cannot go back one more step and leave the app.
- **Decision:** There is only one level of sub-pages. If a sub-page is open, `open(id)` replaces its entry (`history.replaceState`) and adds no new entry. Example: in `trainingsbuch`, "Mit KI eintragen" on the detail of Fran can save a result for Murph and open Murph. The button "Alle Workouts" then shows the list, not Fran.
- **Decision:** The ID is in the hash, not only in `history.state`. A reload or a bookmark then shows the same sub-page. GitHub Pages ignores the hash, so each address loads the same file. If no item has the ID, the app shows the main page. If the tab starts on a sub-page without an entry of the app before it (a bookmark or a link), the hook puts an entry of the main page before it. Thus the back button always shows the main page first and does not leave the app. A reload keeps `history.state`, so after a reload the entries are already there.
- **Decision:** The hook keeps the scroll position of each entry in `history.state` and sets `history.scrollRestoration` to `"manual"`. A sub-page starts at its top. The main page goes back to the place where the user left it. The browser cannot do this itself: it scrolls before React shows the list again.
- **Decision:** Only sub-pages add an entry. Tabs, filters and the selected image in `galerie` do not: a back button that only changes a tab or a filter is not clear, and the user would need many clicks to leave the app. After the back button, the tab and the filters are the same as before, because the app keeps them in React state.
- **Decision:** The back button of the browser does not close a dialog. The apps run only on a computer (Chrome and Edge). There, Esc and the "X" button close a dialog. To close a dialog with the back button, each other way to close it must remove its entry again, and a draft in the dialog would be lost after one click by mistake.
- **Rejected:** A router library (AGENTS.md: no router, and an app has only one level of sub-pages). The Navigation API (`navigation.addEventListener("navigate")`): Chrome and Edge have it, but jsdom does not, so the unit tests would need a fake of it. Paths instead of a hash (`/trainingsbuch/fran`): GitHub Pages has no fallback to the app file.

## 2026-11-18: Exercise filter with Include and Exclude (trainingsbuch)

- **Context:** The workout list of `trainingsbuch` has a filter by exercises: exercises that a workout must have, and exercises that it must not have. AGENTS.md says: UI text is German.
- **Decision:** A workout matches if it has all "Include" exercises (AND) and none of the "Exclude" exercises. The filter works together with the text search, the category and the status. It is not saved: it is gone after a reload, like the other filters of the list.
- **Decision:** A switch with two parts (`ToggleGroup`) at the top of the dialog sets the mode: "Include" or "Exclude". Each time the dialog opens, the mode is "Include". Each exercise is a chip: a tap chooses it in the current mode, a second tap removes it. A chip of the other mode stays visible, but paler, with its icon (✓ or ⃠) and its color. A tap moves it to the current mode. For screen readers, the name of each chip says its mode, for example "Row, 35 Workouts: Exclude".
- **Decision:** The two modes have the English names "Include" and "Exclude". The project owner chose them. All other text of the dialog stays German. Other apps use these words for the same filter (recipe apps for ingredients). The exercise names are English too (see "Workout texts and exercise names in English").
- **Rejected:** Two buttons "Mit" and "Ohne" in each row of the dialog: too much repetition with more than 100 exercises. One chip with three states (a tap for "mit", a second tap for "ohne", a third tap for neutral): a second tap that does not remove the choice is not clear. German words: "Mit / Ohne" and "Enthält / Enthält nicht" were the alternatives.

## 2026-11-18: Launcher icons for apps with AI (launcher)

- **Context:** The first app with AI (`trainingsbuch`) showed two icons on its launcher card: the globe "Nutzt Online-Dienste" and the sparkles. The project owner noted: with AI, a user expects the internet anyway. The globe makes the user think of external APIs, for example holidays or stock prices. The app goes online only for the AI.
- **Decision:** The globe stands only for external APIs: the app info that the build makes from `package.json` (`AppInfo`) has the field `apis`. It is `true` if `pocketApp.connect` is not empty. An app that goes online only for the AI shows only the sparkles. An app with external APIs and AI shows both. The crossed-out Wi-Fi stays for apps with `"network": false`, so an AI app never shows "Nutzt keine Online-Dienste".
- **Decision:** The tooltip of the sparkles names the internet: "Nutzt KI über das Internet, mit deinem API-Key". The user still sees that data goes to a provider.

## 2026-11-18: Record a result with the AI (trainingsbuch)

- **Context:** The project owner wants to record a result from a text or a photo of the whiteboard. The AI asks back when a value is missing. The user confirms the entry before the app saves it. If the AI does not know the workout, it creates a new own workout.
- **Decision:** "Mit KI eintragen" opens a dialog with a chat (`ai-entry-dialog.tsx`). One conversation records exactly one result. The project owner chose this for the first version: one draft keeps the answer shape, the check and the card simple. For several results per conversation, `draft` must become a list, and the card must show each draft with its own save button.
- **Decision:** The conversation lives only in the dialog: it is gone when the dialog closes. The data file keeps only the saved result and, if the AI made one, the new own workout. After "speichern", the dialog closes and the app opens the workout of the result.
- **Decision:** Two ways in. From the list, the instructions (the system prompt) have all workouts as short lines (id, name, scoring, exercises), so that the AI can also find an unnamed workout ("21-15-9 Thruster und Pull-ups" is Fran). From an open workout ("Mit KI"), the instructions have only this workout with its full text. This is cheaper, and the AI does not guess the workout. In this way, the result is always for the open workout: the app ignores another workout ID and a new workout from the AI. The instructions are English, like the workout texts. The AI writes to the user in German.
- **Decision:** The AI answers in one shape (`aiAnswerSchema`): `status` ("question" or "draft"), a German `message` and `draft`. For a question, `draft` is `null`. A draft has nullable fields, for example the score fields that the score type does not use. The exercises of a new workout are an enum of the app, so the provider allows only known exercises. If the input has an exercise that is not in the enum, the instructions tell the AI to ask the user which exercise from the list fits.
- **Decision:** The schema has no limits such as `.min()`: `checkDraft()` checks the values. It checks the workout ID, the day (not in the future), the score for the score type, a time within the time cap, Rx or Scaled for a built-in workout with a weight (else a scaled result without a mark could count as the best result), and, for a new workout, the name, the time cap and the unit of each part (reps, m, cal or s, see `unitsOf()`). If the draft has a problem, the app sends the problem back to the AI, up to two times. These messages stay in the conversation for the next rounds, but the chat does not show them. After the second failed fix, the user sees "Die KI hat keinen gültigen Eintrag geliefert" and can write more details.
- **Decision:** A click outside the dialog does not close it, so that the user does not lose the conversation by mistake. Escape and × close it and cancel a running request. Ctrl+Enter or Cmd+Enter sends a message.
- **Decision:** The AI never saves. The app shows the checked draft as a card. The user saves it, or writes a correction into the chat. A new own workout and its result are saved together.
- **Decision:** The AI gets the text, the photo, the day of today, the unit system (kg or lb) and the workouts. It does not get the results, their notes or anything else from the data file. A photo stays in its message, so it goes to the provider again in each round (from the cache, see "Own AI interface on the official SDKs").
- **Decision:** The catalog has all 253 Hero workouts of crossfit.com/heroes (359 workouts in all). All of them go to the AI with their exercises, so that the AI also finds a Hero workout from a description. The project owner chose this. The alternative was to send only the id and the name of the 221 Hero workouts that came later: about 2,500 tokens more instead of about 8,400 more.
- **Consequence (costs):** We measured the tokens on 2026-11-18 with the free token count of the Claude API. A first request from the list has about 16,800 tokens: the instructions with the 359 workouts, and the answer schema (about 2,700 tokens alone). From an open workout, a request has about 3,500 tokens. A photo adds about 300 to 2,500 tokens. The first round writes the cache (1.25 × the input price). Each further round reads it (0.05 × the input price on these two models). Thus, in US cents, without a photo:

  | Request                    | Claude Sonnet 5.5 | Claude Opus 5.5 |
  | -------------------------- | ----------------- | --------------- |
  | First round from the list  | about 4.5         | about 9         |
  | Further round              | about 0.5         | about 1         |
  | First round from a workout | about 1           | about 2         |

  The dialog "KI einrichten" selects Claude Opus 5.5 by default. The project owner uses Claude Sonnet 5.5 for these apps.

- **Consequence:** `pocketApp` has `"network": true` and `"ai": true`. The app version is 2.0 (a new dialog). The data shape did not change.

## 2026-11-18: Own AI interface on the official SDKs (core)

- **Context:** Apps with AI features need one way to send a request to Claude or OpenAI and to get a checked answer. Some features send images, for example a photo of a whiteboard. The apps have no server, so the browser calls the API directly.
- **Decision:** `packages/core/src/ai/ask.ts` has one small interface for both providers: `askAi(access, request)`. Apps do not call it directly: `useAi()` gives them `state.ask(request)` with the access of the user. A request has instructions, a conversation (messages with a text and optional images), a zod schema for the answer and an optional `AbortSignal`. The function never throws. It returns the parsed data and the tokens, or a failure kind with a German message (`aiMessage`).
- **Decision:** Under the interface, the official SDKs do the work: `messages.create` for Claude and `responses.create` for OpenAI. The helpers `zodOutputFormat` and `zodTextFormat` of the SDKs convert the zod schema to the JSON schema of the provider. Our code validates the answer with `schema.safeParse()`. We do not use the parse methods of the SDKs (`messages.parse`, `responses.parse`): they throw for an answer that does not match, and Claude parses the text before the code can check for a refusal. Thus a wrong answer is `bad-answer`, and a refusal is `refused`. The failure kinds come from the typed errors of the SDKs and the HTTP status (401, 402, 403, 429, 503, 529). An OpenAI error with the code `insufficient_quota` is `no-credit`.
- **Decision:** The request layer lets the SDKs retry twice (`maxRetries: 2`), because a rate limit or an overloaded provider often passes after a short time. The key check in the dialog has no retries: it must answer fast.
- **Decision:** For Claude models that support it (Fable 5.2, Fable 5.1, Opus 5.5, Opus 5, Sonnet 5.5), the request uses server-side fallbacks (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`). If a safety check declines a harmless request, the API runs it again on a fitting model. The interface checks `stop_reason === "refusal"` before it reads the answer. After a fallback, the cost uses the price of the model that answered (`response.model`).
- **Decision:** A request holds a conversation (`messages`), not one text. For a follow-up, the app sends all messages again. Both APIs are stateless: the model reads the full conversation in each round, also with a conversation that the provider keeps. Thus a conversation at the provider (Claude "message threads", beta; OpenAI `previous_response_id`) does not make a round cheaper. It only makes the upload smaller. A Claude thread also expires 5 minutes after the last request, so the app must keep its own copy anyway. Prompt caching makes a round cheaper: Claude requests have the top-level `cache_control: { type: "ephemeral" }` (automatic caching). The API keeps the conversation up to the last message for 5 minutes. In the next round, this part costs 0.05 × the input price on Claude Opus 5.5. The write costs 1.25 × the input price once. OpenAI caches without an extra field. A request with only one round pays the write without a later read. With a photo on Claude Opus 5.5, this is less than 0.2 cents. Look at Claude message threads again if long conversations become slow.
- **Decision:** `pricing.ts` has a copy of the Claude prices (as of 2026-11-18), with the prices of writes to the cache and reads from the cache. Apps show the cost of a request as "ca. … US-Cent". The app does not convert dollars to euro. The list has no OpenAI prices, so OpenAI requests show only the tokens. Update the list when the prices change.
- **Decision:** Unit tests of an app give `useAi()` a fake `ask` function, like the fake `fetchJson`. Tests of the module itself use a fake `fetch`.
- **Rejected:** The Vercel AI SDK (`ai` with `@ai-sdk/anthropic` and `@ai-sdk/openai`). It has one interface for many providers, but it adds one more layer between the app and the API. New features of a provider (for example the fallbacks) can come there later. With two providers, our own layer is small. Look at the decision again if we add a third provider.
- **Rejected:** Direct `fetch` calls with our own JSON schemas. We would have to write the schema conversion and the error handling of both providers ourselves.

## 2026-11-18: Content Security Policy in every app file

- **Context:** Apps with AI features use an API key of the user. A foreign script on the page (for example through a bug or a bad dependency) could send the key to its own server.
- **Decision:** The build writes `<meta http-equiv="Content-Security-Policy" content="connect-src 'self' …">` as the first tag in `<head>` of every app file (`cspPlugin` in `packages/vite-config`). The page code can then call only its own web address, the origins in `pocketApp.connect` and, with `"ai": true`, `https://api.anthropic.com` and `https://api.openai.com`. Each app with `"network": true` lists its APIs in `pocketApp.connect`. The build stops if the list is missing, unless the app has `"ai": true` (then it may call only the AI providers).
- **Decision:** The policy limits only `connect-src`. Scripts and styles are inline in the one HTML file, so a stricter `script-src` would block the app itself. GitHub Pages cannot send headers, so the policy is a meta tag. The dev server gets no policy, because it needs its own WebSocket.
- **Limit:** The policy blocks requests (fetch, XMLHttpRequest, WebSocket, EventSource) to other servers. It does not block all ways out: an image URL or a page change can still carry data. It also does not stop a script that uses the key against the allowed API. Thus the limits at the provider stay important: a spend limit and an expiry date.

## 2026-11-18: AI settings for all apps (core, launcher)

- **Context:** The project owner wants AI features in some apps, with Claude or OpenAI. The apps have no server. The Claude API has no login for the users of a web app: a browser app needs an API key. Both APIs accept requests from the browser (CORS). We tested this from the origin `https://johschmidt42.github.io`, also for rejected keys.
- **Decision:** `packages/core/src/ai` has the AI settings for all apps: `AiSettingsDialog` (provider, key, "Verbindung prüfen", model), `useAiSettings()` and `activeAccess()`. The launcher shows the dialog ("KI einrichten"). An app with `"ai": true` can show it too. The launcher card shows the sparkles icon "Nutzt KI mit deinem API-Key" for these apps. `"ai": true` needs `"stateful": true` and `"network": true`.
- **Decision:** The provider and the model per provider are in `ai/ai.json` in the data folder. They sync with the folder. The file is apart from `launcher/launcher.json`, so the launcher and every AI app read only what they need.
- **Decision:** The API key is not in the data folder. It stays in IndexedDB of the browser (database "pocket-apps", keys `ai-key-anthropic` and `ai-key-openai`), like the folder handle. A research of the options showed: a key in a synced folder is also in the cloud copy, its version history and shared folders. Popular apps with own keys (for example TypingMind) keep the key in the browser too. Cost: the user types the key once per browser and per web address (localhost and GitHub Pages are two addresses).
- **Decision:** "Verbindung prüfen" calls the model list of the provider. It costs no tokens and shows at once if the key works. The same list fills the model choice. For Claude, the dialog selects Claude Opus 5.5 if the key can use it, else the newest model. For OpenAI, it selects the newest model and lists only models for text: IDs that start with `gpt-`, `chatgpt` or `o` plus a digit, without models for images, audio, speech, search or embeddings.
- **Decision:** The calls use the official SDKs `@anthropic-ai/sdk` and `openai` with `dangerouslyAllowBrowser: true`. The key check has no retries. Their typed errors tell a wrong key, a missing permission and no internet apart. In tests, a fake `fetch` replaces the network.
- **Decision:** `ai/ai.json` has no conflict check and no automatic save, unlike the data files of the apps. The dialog writes it only on "Speichern", and only if provider or model changed. The last save wins. The settings change seldom. The file is written before the keys: if the write fails, the browser keeps its old keys. ## 2026-11-17: Image folder with `<input webkitdirectory>` and EXIF thumbnails (core, galerie)

- **Context:** The project owner wanted an app that shows the images of any folder on the computer: a list with thumbnails and a large preview of the selected image. The folders are on a local disk or in Google Drive. A folder can have 2000 photos or more. Before the app, a throwaway prototype measured the options in Chrome 157: with 2901 real photos (9.1 GB, phone photos of about 3 MB each) on a local disk, and with 11 images in Google Drive for desktop in the mode "stream files". All numbers below come from these measurements.
- **Decision:** The app is stateless. The project owner does not want the app to remember folders, so the user picks the folder after each start. The folder dialog is `FolderButton` in `packages/core` (`folder-button.tsx`): a button and a hidden `<input type="file" webkitdirectory>`, like `FileButton`. It gives the app all files of the folder and its subfolders. For the 2901 photos on the local disk, the list was ready after about 0.5 s.
- **Decision:** The app shows only files with an image extension (`image-folder.ts`): JPEG, PNG, GIF, WebP, AVIF, BMP, SVG, ICO and JPEG XL, which Chrome can show, and HEIC, HEIF, TIFF and camera RAW formats, which it cannot show. It skips all other files (for example videos, PDFs and text files) and hidden files that start with a dot.
- **Decision:** A thumbnail comes from the EXIF preview image first (`exif-thumbnail.ts`). Cameras and phones put a small JPEG (about 160 × 120 pixels) into the EXIF data of a photo. The EXIF data is at the start of the file and is at most 64 KB long. The app reads the first 128 KB, because some other blocks can come before the EXIF data. 2777 of the 2901 photos had an EXIF preview image. Without one, the app decodes the full file with `createImageBitmap()`, scales it to 160 pixels width and keeps a small WebP. For all 2901 photos: EXIF first took 2.9 s and read 0.55 GB (128 KB of each photo, plus the full file of the 124 photos without EXIF preview image). Decode only took 46 s and read all 9.1 GB.
- **Decision:** The EXIF preview image is stored without the EXIF orientation of the photo. Thus the app turns it with a Tailwind class (`rotate-90`, `rotate-180` or `-rotate-90`). The thumbnail box is square and the image fills it (`object-cover`), so a turned image needs no other layout. The mirrored orientations (2, 4, 5 and 7) are rare. The app turns them like the nearest orientation without the mirror.
- **Decision:** Only the rows on the screen (and 200 px around them) load a thumbnail (`IntersectionObserver`, `thumbnail-queue.ts`), at most 6 at the same time. The reason is Google Drive in the mode "stream files": it downloads the full file at each read. A test that read only the first 4 KB of a file also downloaded the full file. Each download took about 1.3 s, but parallel downloads were much faster (6 files in 1.6 s). Thus the EXIF preview image saves no download in Drive, and to make all thumbnails at once would download all photos of a Drive folder (gigabytes). The mode "mirror files" keeps all files on the disk, so it is as fast as a local disk. We measured only 11 files in Drive. Check the numbers again with a large Drive folder.
- **Decision:** The thumbnails are only in memory, as object URLs. The app frees them when the user picks another folder (`queue.stop()`).
- **Decision:** The preview uses an object URL of the image file. The app makes the object URLs of all images at once, when the user picks the folder (in the event handler), and frees all of them at the next pick. An object URL reads nothing, so this is cheap. The alternative is an effect that makes the URL of the selected image and puts it into state. The project rules forbid effects that set state when the value can come from elsewhere (ESLint `react-hooks/set-state-in-effect`). While the image loads (in Google Drive, a second or more), the preview says "Lädt …".
- **Decision:** The arrow keys, Home and End select another image, wherever the focus is on the page (a `keydown` listener on `window`). The focus follows the selection in the list. A key does nothing if a component already handled it (`defaultPrevented`, for example the theme switch, a Radix toggle group of shadcn) or if Ctrl, Alt or Cmd is pressed. The app has no text fields. If a later version adds a text field or a select box, the listener must skip keys from it.
- **Limit:** Chrome and Edge cannot show HEIC (iPhone photos), TIFF and RAW files. The list shows the format (for example "HEIC") instead of a thumbnail. The preview says that the browser cannot show the format. Google Photos is not a folder: the app cannot open it. Since March 2025, the Google Photos API lets an app read only the photos that this app uploaded.
- **Limit:** The list renders all rows. With 2901 rows, this took 6 ms. Check this again for folders with much more than 10 000 images. Then a virtual list (which renders only the visible rows) can be necessary.
- **Rejected:** `showDirectoryPicker()` (File System Access API). It can keep the folder in IndexedDB, but the app must not remember folders. `<input webkitdirectory>` is as simple as `FileButton`, and Playwright can fill it (`setInputFiles` with a folder). It also works in Firefox and Safari, but the project still tests only Chromium. Drawback: Chrome calls the pick an "upload" ("Dateien hochladen?"). The start screen explains that no file leaves the computer.
- **Rejected:** A cache for the thumbnails in the browser or in the data folder (faster at the second start, but the app would need storage), and a Web Worker (not necessary with EXIF preview images).

- **Context:** In `lebenslauf`, each variant of the CV can have its own photo. The photo is somewhere on the computer of the user. It can keep a handle to the file (like the handle to the data folder), but the handle stays in this browser. On a second computer with the same synced data folder, the photo would be missing.

A conflict is rare, and no other data is lost.

## 2026-11-16: Drag and drop with a grip handle (lebenslauf)

- **Context:** The user wanted to change the order of contact lines, sections and entries by drag and drop, not with arrow buttons: a grip icon at the left of each row, hold the mouse button and move the row.

The drag image (the picture that moves with the mouse) is the whole row, not only the icon. The data type is an own type (`application/x-pocket-apps-sort`), not `text/plain`: else a text field takes the drop and inserts the ID. The element around the rows is the drop zone. - **Tests:** `userEvent` cannot drag with the drag API of the browser, and `AGENTS.md` wants `userEvent`, not `fireEvent`. Thus the unit tests check the keyboard and the pure functions (`moveTo`, `dropPosition`). `e2e/lebenslauf.spec.ts` drags with Playwright in Chromium.

## 2026-11-16: CV designs with own CSS in an iframe (lebenslauf)

- **Context:** `lebenslauf` keeps a CV with variants, for example one variant per job ad. It shows the CV of the active variant as an A4 sheet and prints it as a PDF. The first design ("klassisch") copies the Word CV of the user: a blue name box, gray bands with blue section titles, italic labels and a blue line before each text. The look of a CV is the content of the app, not its UI. It needs exact sizes in mm and pt, fixed colors, a white sheet in dark mode, and print rules (`@page`, page breaks).
- **Decision:** The preview is an `<iframe>` with its own document (`cv-frame.tsx`). React renders the CV into the body of the frame with a portal. Each design has one CSS file (`src/designs/<design>.css`). `src/designs/designs.ts` imports it as text with the Vite suffix `?inline` (Vite then gives the file content as a string and does not add it to the page). The frame puts the text into a `<style>` element. Thus the CSS of the design does not reach the app, and Tailwind does not reach the CV. "Drucken / PDF" calls `print()` of the frame window. Chrome then prints only the CV, and `@page { size: A4 }` applies.
- **Decision:** The ESLint rule `no-restricted-imports` allows the import of CSS as text only in `apps/*/src/designs/`, and only as `./<name>.css?inline`. All other CSS imports stay forbidden in all app files, also a plain `./x.css` in `src/designs/`. Before, the pattern `*.css` did not match `x.css?inline`. Now the rule also forbids CSS imports with a query (`*.css?*`). The CSS rules of `AGENTS.md` (Tailwind only, theme colors) stay for the UI of all apps, including the editor of `lebenslauf`.
- **Decision:** The design CSS has four `eslint-disable` comments for `css/use-baseline`: `@page`, `print-color-adjust`, `break-after: avoid` and `box-decoration-break` are not "widely available" in all browsers. Chrome and Edge support them, and the apps support only Chrome and Edge.
- **Decision:** The data shape belongs to the design. `Variant` is a discriminated union with the field `design`. The design "klassisch" has three kinds of sections: `projects` (title, description, tasks, tools), `stations` (from, to or "since", title, subtitle, bullet points) and `list` (label and values). The user picks the design in the dialog "Neue Variante". (Update: since the design "modern", all designs have the same fields, and a variant can change its design. See "Second CV design".) The language of a variant (`de` or `en`) changes only the fixed words of the design, for example "Description" and "Beschreibung" (`src/designs/labels.ts`). Name and contact lines are in the field `person` of the data file, outside the variants. Thus they are the same for all variants. A new variant starts empty. The title of a section is a button. A click on it (or Enter or Space on the keyboard) turns it into a text field (`section-title.tsx`): Enter or a click outside saves, Escape keeps the old title. The user did not want a pencil button for this. The dialog "Neuer Abschnitt" only adds sections, because there the user also picks the kind. "Duplizieren" copies a variant with all its sections. The copy, its sections and its entries get new IDs.
- **Decision:** The app uses the full width of the window. In a window of 1280 px or more (the Tailwind breakpoint `xl`), the editor column is at most 640 px wide, because wider text fields do not help, and the preview gets the rest of the width. Between 1024 px (`lg`) and 1280 px, editor and preview share the width 2 : 3. Below 1024 px, the toggle "Bearbeiten" / "Vorschau" shows one of the two columns. On screen, the frame scales the A4 sheets with a gray space of 6 mm around them to its width with CSS `zoom` in the frame document. The gray space at the top shows where the first page starts. The zoom is smaller in a narrow column, and up to 150 % of the real size (210 mm wide) in a wide column. The box around the frame has an outline from a shadow (the Tailwind class `ring`), not a `border`: a border would make the box 2 px wider than the frame, and the sheet then overflows the frame. The frame gets the height of its content.
- **Decision (pages):** The preview shows the CV as A4 sheets, split as in the print. The user wanted to see the pages, not a line at each page end. It works in four steps:
  1. The design marks each block that the print keeps on one page with the attribute `data-page-unit=""`: the head, a project, a station, a list row. These blocks also have `break-inside: avoid` in the CSS. A section title has `break-after: avoid` in the CSS and `data-page-unit="keep-with-next"`.
  2. The frame renders the CV once as one long sheet. This copy is invisible (`opacity: 0`), but screen readers still read it, and the print prints it.
  3. The frame measures the marked blocks in this copy. `paginate()` (`pages.ts`) computes where each page starts: a block that does not fit goes to the next page, and the `keep-with-next` title before it goes with it. A block that is higher than a page is split at the page end.
  4. For each page, the frame renders one white sheet with another full copy of the CV. A box in the sheet with `overflow: hidden` shows only the part of the page: the copy has a negative top margin (it moves up to the start of the page), and the box is as high as the page content. These per-page sizes are CSS rules that `frameCss()` (`cv-frame.tsx`) writes as text into a `<style>` element of the frame. The sheets have the attribute `inert`: the keyboard and screen readers ignore them.
- **Decision (pages):** The print hides the sheets and prints the copy of step 2. Chrome then splits the pages with the same rules. `e2e/lebenslauf.spec.ts` checks that the preview and the PDF have the same number of pages. Each design states its page margin in `DESIGN_INFO` (`src/designs/designs.ts`, the list of all designs): `pageMargin`, 12 mm for "klassisch". It is the padding at the top and at the bottom of the CV sheet. The frame needs it to know where the content of a page starts and how high it is. If the frame has no layout (it is hidden, or in jsdom), the frame shows the CV as one sheet without pages.
- **Rejected (pages):** Paged.js (a library that imitates the print in the browser: large, and it changes the DOM that React renders). CSS columns with the height of a page (they use the same break rules as the print, but they put the pages next to each other, not one below the other).
- **Detail:** The frame uses `srcdoc` with a doctype, so the CV document is in standards mode. Chrome loads the `srcdoc` after the frame is in the page. Until then, the frame has an empty first document without a body. While Chrome loads the `srcdoc`, the new document can have no root element (`<html>`) for a moment, although the type of `documentElement` does not allow `null`. Thus the frame takes the root element with `querySelector("html")`. ## 2026-11-16: Raw view of the data file with an own JSON tokenizer (core)

- **Context:** The status line shows where the data of an app is (folder and file name). The user wanted to see the raw data of the file, but not to change it there.
- **Decision:** A click on the folder and file name opens a dialog (`raw-data-dialog.tsx` in `packages/core/src/data-file`). The store reads the file again from the folder. Thus the dialog shows what is really in the file, not the data in memory. The dialog shows the JSON text with an indent of 2 spaces in a `<pre>`. It has no text field. The same view is in the error message of a broken file, as the button "Rohdaten ansehen" ("show the raw data"): there, the raw data helps most. `RawDataButton` holds the button, the dialog and its state for both places. On the file name, the hint "Rohdaten ansehen" is a `Tooltip` from `packages/ui`, not a `title` attribute: the browser shows a `title` only after a delay, and the user wanted the hint at once. The hand cursor (`cursor-pointer`) tells that the name is a button.
- **Decision:** Colors come from an own small tokenizer (`json-tokens.ts`): one regular expression splits the JSON text into parts (keys, strings, numbers, literals, punctuation, space), and each part gets a color. Keys use `--chart-7` (purple). Numbers, `true`, `false` and `null` are bold in `--foreground`. Strings use `--foreground`, and punctuation uses `--muted-foreground`. Keys are not a chart category. But `AGENTS.md` allows no new colors, and the chart colors are the only colors of the theme besides gray and the primary color. `--chart-7` on `--muted` (the background of the text) has a contrast of 5.3:1 (light) and 4.9:1 (dark). `--chart-1` (blue) was rejected: it has only 4.1:1 there, less than the 4.5:1 that WCAG needs for small text.
- **Decision:** A text that is longer than 100 000 characters (counted with the indents) shows without colors. A colored text has one `<span>` element for each token (key, string, number, punctuation, space). Many thousands of elements make the dialog slow to open. For example, the data file of the app `kursverlauf` (price history of ETFs) is about 245 KB.
- **Rejected:** A JSON viewer library (for example a tree view with folding). It adds a dependency for a small feature, and AGENTS.md wants browser APIs first. A text field with the attribute `readonly`: it looks like the user can change the text.

## 2026-11-14: Vertical timeline drawn as own SVG, not with Recharts (zeitstrahl)

- **Context:** `zeitstrahl` shows moments (points) and time ranges on vertical timelines, for example a CV or the appointments at a doctor. Time goes from top to bottom. A line is in the middle. Each entry is left or right of the line. The user picks the side per entry (field "Seite"). The default "Automatisch" takes the other side of the entry before it. Two views: real distances, or long empty gaps cut short ("Lücken kürzen"). A gap is long if it is more than 10 % of the whole time. A cut gap is 48 px high: a dotted part of the trunk, with the real length as a chip ("6 Jahre").
- **Decision:** The app draws the timeline as its own SVG (`timeline-chart.tsx`). The calculations are pure functions in `layout.ts`: the scale with its cut gaps, the ticks, and the positions of the cards. This is an exception to "charts use Recharts" (2026-11-10: Charts with Recharts).
- **Why:** Recharts has no axis in the middle of a chart and no broken axis (an axis with cut gaps). With Recharts, the app would use only `ResponsiveContainer` (it measures the size). All marks and the axis would be own code anyway, and Recharts would add about 155 KB (gzip) to the app file.
- **Decision:** The SVG uses percent values for the horizontal positions (`x="50%"`). A nested `<svg x="50%">` puts the origin on the center line. Thus the code gives all positions as SVG attributes and needs no inline `style`. Each entry has a card: HTML in a `<foreignObject>`, a `<button>` with Tailwind classes. A card with a description shows a `Tooltip` from `packages/ui` with it. A click on a card opens the dialog "Eintrag bearbeiten".
- **Decision (look):** The look follows popular timeline examples (Cruip "Progress Timeline" with Tailwind, shadcn timeline blocks, Linear and Notion): white cards with a thin border and a soft shadow on a light gray area, and a small rounded label ("chip") on the line for each tick (years or months: the app takes the smallest step that keeps the chips at least 56 px apart). "Heute" and each cut gap are chips on the line. While the mouse is on a card, the other entries fade.
- **Decision:** The app has no list of entries. The cards show the title, the date and, for a range, its length ("5 Jahre"). A click on a card opens the dialog "Eintrag bearbeiten". An eye button on each card hides the entry: the data file sets the field `visible` of the entry to `false`. Hidden entries are not on the timeline, and the scale ignores them. If there are hidden entries, the toggle button "Ausgeblendete zeigen (2)" (with the number of hidden entries) appears above the timeline. When it is on, the timeline also shows the hidden entries, with faded cards and dashed lines, and the scale includes them. Their eye button shows them again. While the toggle is on, an entry that the user hides stays on the timeline as a faded card. When the last hidden entry comes back, the toggle goes off. The data file does not keep the toggle: after a reload, it is off. An earlier version had one chip per entry above the timeline. We removed it: it repeated the cards, and the user wanted the control on the entries. The button "Neuer Eintrag" above the timeline adds an entry. The dialog "Eintrag bearbeiten" removes an entry. A row of toggle buttons ("pills") above selects the timeline, not a select box.
- **Decision (trunk):** The user wanted a thick line in the middle of the timeline, with the entries growing from it like branches. The line is a trunk: a rounded bar, 18 px wide, in `--muted-foreground` at 30 % opacity. For each entry, a branch grows from the side of the trunk that the entry is on to the card. A branch is a filled shape between two curves from the edge of the trunk to the inner edge of the card, in the color of its side (`--chart-1` left, `--chart-2` right). At the trunk, the branch of a range goes from the position of its start to the position of its end on the time scale (at least 10 px). Thus a long range has a wide branch, like a fan. The branch of a point is 10 px wide at the trunk and has a ring (6 px radius) on the edge of the trunk. At the card, each branch is 3 px wide. Overlapping ranges on one side have overlapping branches. The fill is light (35 % opacity) and the outline is strong (80 %). Thus each branch stays visible. An earlier version had thin lines and a colored bar per range next to the line, in up to 3 lanes. The user found the bars out of place.
- **Decision:** The SVG draws the branches first, then the trunk with its chips, then the rings. A year chip that a ring would cover (nearer than 15 px) is left out. A point with year precision is always on a year chip, so this happens often.
- **Decision (leaves):** A card is a leaf at the end of its branch. It has a leaf shape: two opposite corners are round (20 px), the other two are small (6 px). On a card right of the trunk, the top left and the bottom right corners are round. On a card left of the trunk, the top right and the bottom left corners are round. The card has a light tint of the side color (`--chart-1` left, `--chart-2` right, at 8 % opacity) on its full area, and a border in the side color (30 %, 60 % while the mouse is on the card). It shows the title in bold and one gray line with the time and the length: "10/2018 – 09/2021 · 3 Jahre". A small, light icon (`MessageSquareText` from lucide) after the title tells that the entry has a description. The eye button that hides the entry shows only while the mouse is on the card or the keyboard focus is in it. This applies only to a device with a mouse or a touchpad (the Tailwind variant `pointer-fine`). On a touch screen, it always shows, because there is no mouse. On a hidden card (dashed border, faded), the eye button always shows: there, showing the entry again is the main action. The hint "Ausblenden" or "Einblenden" shows at once below the eye button (`HintTooltip`, a `Tooltip` of `packages/ui`), not after the delay of a `title` attribute. Below, because the description bubble can be above the card. Earlier versions had a colored stripe in the card, a tint that faded out in the middle of the card, the date as a chip in the card, and an eye button on each card. The user found this not calm and the eye button not clear: a crossed-out eye on a visible entry looks like a state, not like an action.
- **Decision (description):** The description shows in a bubble at the outer side of its card (left of a card on the left, right of a card on the right). When the bubble opens, `bubblePlace()` measures the space between the card and the edge of the window. It takes the widest bubble width that fits there completely: 320, 240 or 200 px. The space must also hold 22 px for the stem and a margin, on top of the bubble width. If not even 200 px fit, the bubble goes above the card with 320 px (below it, if there is no space above). The bubble must fit with its full width before it opens. If it does not fit, Radix moves it to the opposite side of the card (the inner side, over the trunk). Radix makes a bubble narrower only after this move, so a narrower maximum width from Radix does not help. The bubble has the leaf shape and a border in the color of the side. A stem connects bubble and card, in the style of the branches (the color of the side, light fill, strong outline): 8 px wide at the card, 2 px wide at the bubble. The stem is vertical above or below the card and horizontal at its side. The bubble opens when the mouse is on the card or when the card has the keyboard focus. The bubble is the `Tooltip` of `packages/ui` with own classes: it hides the arrow of the tooltip, because the stem replaces it. The app never chooses the inner side: there the bubble would cover the trunk. Because the app chooses a width that fits, Radix never moves the bubble there. The user asked for the bubble at the side, not above. The bubble has nothing to click, so it has `pointer-events-none`. It also has `disableHoverableContent`. Without it, Radix sets a mark in the shared `TooltipProvider` (`isPointerInTransitRef`) when the mouse leaves the card in the direction of the bubble. If the app closes the bubble during this move, the mark stays set. Then Radix opens no other tooltip of the page. The app decides when a bubble is open, not Radix (`useActiveCard()` in `use-active-card.ts`). The hook listens to each mouse move in the document and asks which card is under the mouse. Radix puts each bubble into a box (`div[data-radix-popper-content-wrapper]`). The class `pointer-events-none` reaches only the bubble in it, so this box still takes the mouse. If the mouse is on this box, `document.elementsFromPoint()` gives the card below the bubble. During a scroll, no card is active. At the end of a scroll (`scrollend`), the card under the resting mouse becomes active. Escape closes the bubble of the active card (the card under the mouse or with the keyboard focus). A click on the card also closes it, because the click opens the dialog "Eintrag bearbeiten". Each card keeps the place (side and width) of its bubble, also after it is no longer the active card. In an earlier version, the hook had one place for all cards: when the mouse left a card, the place went back to "above", and the bubble jumped above the card during its fade-out animation (about 150 ms). The keyboard focus in a card also opens its bubble. Before, Radix and each card used the `pointerenter` and `pointerleave` events of the card. A Playwright script (not in the repository) made 300 random mouse moves over the timeline. After each stop, it checked that the open bubble belonged to the card under the mouse. With the old way, sometimes such an event got lost: then no bubble opened, or a wrong card stayed active (up to 7 of 96 stops). With the new hook, the script found no error at the window widths 380, 1000, 1300 and 1440 px. In an earlier version, a card also moved up by 2 px on hover. Then a mouse at its bottom edge was suddenly outside the card, and the card lost the hover. Now a card does not move on hover. A card that opens the dialog "Eintrag bearbeiten" shows the hand cursor (`cursor-pointer`).
- **Decision (dates on the trunk):** While a card is active (the mouse is on the card or on its branch, or the card has the keyboard focus), date chips on the trunk show where its branch touches the trunk: the start and the end of a range, or the date of a point (a moment). An ongoing range has only its start, because "Heute" is its end. If the two chips of a range would be nearer than 22 px on the trunk (from center to center), one chip in the middle of the range shows the whole range, for example "02/2016 – 07/2016". The chips sit in the middle of the trunk, like the year chips, with a border in the color of the branch. Year chips nearer than 20 px are left out while the date chips show. The date chips let the mouse through. The cards already show their dates, but the year chips are too coarse to show where a range starts and ends on the trunk. A second bubble with the dates was rejected: it would repeat the card. A branch and the ring of a point have the attribute `data-branch-of` with the ID of their entry. Thus `useActiveCard()` finds the card of a branch, and the mouse on a branch works like the mouse on its card.
- **Decision (description format):** A description has a small own format with three rules: a line that starts with `-`, `*`, `•` or `·` and a space is a list item; `**text**` is bold; an empty line starts a new paragraph. A single line break inside a paragraph stays a line break. Other text stays as it is, also a single `*` and an unclosed `**`. `description.ts` parses the text into paragraphs and lists, and `description-text.tsx` renders them as React elements, never as HTML. Thus a description cannot inject code. The dialog shows the rules under the field. Rejected: full Markdown (headings, tables and links are too much for a short description, a link in a hover bubble is hard to click, and it needs a library), and a format that guesses (for example "the first line is a heading"), because a wrong guess looks broken.
- **Decision (trunk color):** A click on the trunk gives it the next color: gray (the default, `--muted-foreground` at 30 % opacity), green (`--chart-3`), purple (`--chart-7`), pink (`--chart-5`), yellow (`--chart-4`), red (`--chart-8`), then gray again. The colors have 55 % opacity. `--chart-6` is not used: it is too near to `--chart-3`. The data file keeps the color per timeline in the field `trunk`, with the values `gray`, `green`, `purple`, `pink`, `yellow` and `red`. Schema version 1 was not published yet, so the field needs no migration. The trunk is not a category, but `AGENTS.md` allows no new colors, and `--chart-1` and `--chart-2` are the sides. To make the trunk clickable, a transparent `<button>` in a `<foreignObject>` lies on the trunk. Its `aria-label` tells the current color. While the mouse is on the trunk, a dark chip "Klicken: Farbe ändern" shows on the trunk. On each mouse move, the trunk button gives the height of the mouse (`offsetY`), and the chip moves to this height. A `Tooltip` was rejected: Radix puts it at the middle of its trigger, and on a long trunk this is far from the mouse. Each card is in an invisible box (a `foreignObject`) that reaches to the middle of the trunk. The visible card stops 64 px before the trunk. Thus the `foreignObject` elements have `pointer-events-none`, and only the cards in them take pointer events. Else a click on the trunk worked only between the cards.
- **Decision:** Cards on one side that would overlap move apart vertically as a group (60 px per card, 10 px space). The group is centered on the mean of their start dates. The branch of a moved card bends more.
- **Decision (example):** A new data file has one empty timeline, "Mein Zeitstrahl". While no timeline has an entry, the app shows an example CV with a short notice. The example is a constant in `example.ts`, not data in the file. Its cards have no click and no eye button, but they show their descriptions. The first own entry replaces the example. An empty timeline next to timelines with entries shows only the text "Noch keine Einträge".
- **Decision:** Below a width of 600 px, the timeline has one column: the line on the left, all cards right of it. Two columns at a width of 480 px give each card less width than one column at 320 px. Thus the limit is 600 px, not 480 px. The line has at least 90 px per entry, at least 400 px and normally at most 1600 px. But it is always long enough for the cards of the side with the most cards (70 px per card). This rule wins over the 1600 px. Else, in one column with 30 entries, the last cards are hundreds of pixels below their marks. A `ResizeObserver` measures the width. The color still shows the side that the entry has in two columns (`--chart-1` left, `--chart-2` right). Thus a user can use the sides as two categories, for example "Ausbildung" and "Beruf".
- **Decision:** An entry has a precision: day (`"2026-11-14"`), month (`"2026-11"`) or year (`"2026"`). The data file stores the date as this text. The precision comes from the form of the text. A range includes its last day, month or year: "2015 – 2020" ends on 2021-01-01. If both ends of a range are days of the same year, the card shows the year only once: "01.02. – 03.03.2026". With this short form, the date of such a range fits into a card at a window width of 320 px.
- **Decision:** `fixkosten` and `zeitstrahl` both need a dialog for the name of a new item (a profile, a timeline) and `isOneOf()`. Both moved to `packages/core` (`NameDialog` in `name-dialog.tsx`, `isOneOf` in `one-of.ts`). `fixkosten` looks and works the same, so its version did not change.
- **Rejected:** The rules in `AGENTS.md` forbid CSS files in apps and inline `style`, and need the theme variables for dark mode. vis-timeline (fits well, but changes the DOM itself, needs its own CSS file and moment, about 122 KB gzip, and its React wrappers are from 2020). react-calendar-timeline (only beta versions, own CSS). react-chrono, vertical-timeline-component-react and the shadcn timelines of ReUI (even steps, no real time scale). dnd-timeline (gives positions as inline `style`). timelines-chart (d3, no theme). d3fc-discontinuous-scale (a scale with gaps, but our scale is about 30 lines). SVAR, Mobiscroll, DayPilot, TimelineJS (other design systems, commercial, or slide shows).
- **Cost:** The app file is about 556 KB (165 KB with gzip). That is about 75 KB more than `countdown` (a stateful app without charts), because of the tooltip, the toggle group and the select box. `fixkosten` with Recharts is about 970 KB (281 KB with gzip).

## 2026-11-10: School holidays from OpenHolidays, calendar with react-day-picker (schuljahr)

- **Context:** `schuljahr` shows a school year of one German state: the school holidays, the public holidays and the school days. It also counts, for example, the school days until the next holidays.
- **Decision:** The data comes from the OpenHolidays API (`openholidaysapi.org`). The API needs no key and allows requests from all web addresses (CORS `*`). The data has the license ODbL. Thus the app shows the source and the license under the calendar.
- **Decision:** The app loads a school year only when the user selects it for the first time. The button "Neu laden" loads the shown school year again (only this one). The app stores the result in the data file. At the start, it reads the data file and sends no request. Thus the app also works without internet for all stored school years.
- **Decision:** A school year goes from August 1 to July 31 (as the Kultusministerkonferenz, KMK, defines it). The app loads the data until September 30 after the school year. In Bayern, the summer holidays at the end of a school year start in August, after July 31 (2027: August 2 to September 13). With the extra two months, the app has these summer holidays complete, and it can count the school days until they start.
- **Decision:** The app shows the dates of the general schools (allgemeinbildende Schulen) in the whole state. `parseHolidays()` keeps an entry only if all three rules are true:
  - The entry is for all of Germany (`nationwide`), or its `subdivisions` contain the code of the state (`DE-BY`). An entry only for a city (Augsburg: `DE-BY-AU`) fails.
  - The field `tags` does not contain `Exception`. OpenHolidays uses this tag for a part of a state, for example the North Sea islands in Schleswig-Holstein.
  - The entry has no `groups`, or one group code ends with `-ABS` (general schools). An entry only for the vocational schools (`DE-MV-BBS`) fails. In 2026, only Mecklenburg-Vorpommern has groups.
- **Decision:** School days are Monday to Friday, without school holidays and without public holidays. OpenHolidays does not know the movable free days (bewegliche Ferientage) that each school sets itself (for example in NRW). The app says this under the calendar.
- **Decision:** The calendar is `DayPicker` from react-day-picker 10. `packages/ui/src/day-picker.ts` exports it, like `charts.ts` exports Recharts. ESLint forbids a direct import of `react-day-picker` in apps. The app gives all styles as Tailwind classes (`classNames`). It does not use the CSS file of react-day-picker.
- **Why:** The shadcn component `calendar` uses react-day-picker too. But its code does not pass our typecheck: it passes `locale`, which can be `undefined`, to a prop that does not allow `undefined` (`exactOptionalPropertyTypes`). We do not change vendor code. `DayPicker` gives the grid of the months, German names, Monday as the first day and labels for screen readers. Each day has a label with its holidays, for example "Mittwoch, 18. November 2026, Buß- und Bettag".
- **Decision:** The calendar shows only the months from the first to the last school day of the selected state. Example: in Bayern, school starts in mid-September. Thus the calendar starts with September. In a state where school starts in August, it starts with August. The totals (for example "185 Schultage" and "93 Ferientage") still count the whole school year from August 1 to July 31.
- **Decision:** A coloured day shows a tooltip with all its holidays, for example "Weihnachtsferien, Feiertag: 1. Weihnachtsfeiertag". The app replaces the `Day` component of DayPicker. DayPicker gives this component only the date and its modifiers (flags of DayPicker such as "today" or "hidden"), no other props. Thus `year-calendar.tsx` gives the tooltip texts (a map from the date to the text) to the cells through a React context. A module-level variable is no alternative: when the user selects another school year, the cells would not render again.
- **Decision:** The context also gives the cells a hover handler (mouse enter and leave). While the mouse is on a coloured day, the calendar puts a frame around all days of the holiday that gives the day its color (a public holiday wins over school holidays). The list gives the entry of this holiday a gray background. The list does not scroll. The same happens the other way: the mouse on a list entry frames its days in the calendar. The cursor stays the arrow, not the hand: the hand means "click here", but a click on a day does nothing.
- **Decision:** `fetchJson` moved from `kursverlauf` to `@pocket-apps/core/fetch-json`, because two apps use it now. ESLint forbids this import in apps with `"network": false`, like `fetch`.
- **Cost:** The app file is about 530 KB (156 KB with gzip). That is about 50 KB more than `countdown`, a stateful app without a calendar.
- **Rejected:** ferien-api.de (refused each request with HTTP 429 "Too Many Requests" in a manual test with curl). mehr-schulferien.de (the Buß- und Bettag in Bayern is missing). FullCalendar (own CSS files and a large bundle). react-yearly-calendar (old, own CSS). HeroUI, SVAR, Syncfusion (other design systems).

## 2026-11-10: 3D graphics with three.js (attraktor)

- **Context:** `attraktor` shows a strange attractor: a chaotic system of formulas. Points follow the formulas, and their trails are glowing 3D lines that move slowly. The mouse pulls on the lines. The first attractor (Aizawa) copies the start page of zensical.org.
- **Decision:** The app draws with three.js 0.187 (WebGL 2, the 3D graphics interface of the browser). three.js is a dependency of the app, not of `packages/ui`, because it is a graphics library and not a component library. If a second app needs it, move the shared code into a package.
- **Why:** zensical.org uses three.js for this picture: 225 lines with 192 to 384 points each (about 65,000 points), additive blending (the colors of lines that cross add up) and a glow effect after the render (`UnrealBloomPass`). three.js gives all of this.
- **Cost:** The app file is about 914 KB (246 KB compressed with gzip). three.js adds about 150 KB of it. Other apps do not get it.
- **Decision:** The picture is always dark, also in light mode. Added light needs a dark background. The line colors are hex values in `palettes.ts`, not theme variables, because WebGL cannot read CSS variables. The small color bars of the color choice (`palette-swatch.tsx`, SVG) use the same hex values, so that they show the colors of the picture.
- **Decision:** The simulation and the mouse effects (the mouse bends the picture, pulls on the points, or pulls the lines like rubber) are plain TypeScript in `simulation.ts`, `mouse-effects.ts` and `attractor-scene.ts`. They run on the CPU. three.js only draws (`webgl-view.ts`). Thus unit tests cover all logic.
- **Decision:** The unit tests run in jsdom, which has no WebGL. Thus `webgl-view.test.ts` replaces two three.js parts with fakes (`vi.mock`): the WebGL renderer and the chain of effects after the render (glow, colors). The camera, the mouse ray (the line from the camera through the mouse pointer) and the line geometry are the real three.js classes. For the same reason, `App` has the optional prop `viewFactory`. Only the tests use it: they give a view that records the calls and draws nothing. All other code (scene, simulation, mouse, React) runs as in the browser.
- **Decision:** `e2e/attraktor.spec.ts` starts Chromium with the flags `--use-angle=swiftshader --enable-unsafe-swiftshader`. CI computers have no graphics card. With these flags, Chromium calculates WebGL in software (SwiftShader).

In the full screen, the same button ("Vollbild beenden") and the Esc key end it. Without the Fullscreen API (for example on an iPhone), this button is not there.

The tooltips of `packages/ui` show in an element at the end of `<body>`. With only the picture in full screen, the browser does not show them. jsdom has no Fullscreen API. Thus `app.test.tsx` adds a small copy of it, as the tests do for `getBoundingClientRect`.
- **Detail:** The values of Aizawa come from the page code of zensical.org. The formula has 6 parameters (α to ζ). ## 2026-11-10: ETF prices from Alpha Vantage (kursverlauf)

- **Decision:** `kursverlauf` gets the prices from Alpha Vantage, with a free key that the user types in. The free key allows 25 requests per day and 1 request per second.
- **Decision:** The app uses only the weekly prices (`TIME_SERIES_WEEKLY_ADJUSTED`). With the free key, daily prices go back only 100 days, but weekly prices go back to the start of the ETF (for example 2011). One request per ETF gives all of it. The newest entry is the close of the last trading day, also in a week that is not complete. There are no live prices.
- **Decision:** The app shows the close with splits corrected, but not adjusted for dividends. Alpha Vantage gives two values per week: the close and the adjusted close (adjusted for splits and dividends). The app compares the ratio "adjusted close / close" of each week with the ratio of the next newer week. If the ratio changes by more than 1.5 times (up or down), there was a split. The size of this change is the split ratio (for example 1/25). The app multiplies all older closes by it. A dividend changes the ratio by a few percent only, so the app ignores it. Example: the 25:1 split of SPDR MSCI ACWI IMI (IE00B3YLTY66) on 2026-02-23.
- **Decision:** The data file keeps only the last download per ETF. A new download replaces it. A failed download keeps the old data, and the app shows a German message on the card of that ETF.
- **Decision:** At the start, the app downloads the ETFs whose download is from an earlier day (local time of the computer), or that have no download. It tries each ETF once per session automatically. The button "Kurse aktualisieren" downloads only the ETFs with an error, without prices, or with a download older than 1 hour. Else the button is off. Thus 3 ETFs need about 3 requests per day. A new key tries all ETFs again. If the user reaches 25 requests in a day, the app says so.
- **Decision:** The app sends one request to Alpha Vantage at a time, at least 1.5 seconds apart. Alpha Vantage answers each refused request with HTTP 200 and a JSON field `Information`. The text tells the reason: "per second" or the daily limit. The app shows a message and does not try again by itself.
- **Decision:** The search by ISIN or ticker uses Twelve Data (`symbol_search`). The search needs no key. Only the prices of Twelve Data need a paid plan (see "Rejected"). The app keeps the hits with `mic_code` `XETR` (Xetra), because Alpha Vantage has prices for Xetra. It adds `.DEX` to the ticker: `VGWL` becomes `VGWL.DEX`. The names of Twelve Data are not always right, so the user can change the name before the app adds the ETF.
- **Decision:** The comparison chart starts all lines at the first date that all ETFs have. Else an ETF with a longer history would compare a longer time. Below the chart, a list shows the change of each ETF as text.
- **Decision:** The comparison has the option "Mit Ausschüttungen". Then it uses the adjusted close of Alpha Vantage (splits and dividends). Without it, a distributing ETF looks worse than an accumulating ETF, because its price drops by each dividend. The cards always show the real close.
- **Migration (schema version 2, app 2.0):** Each stored price got the second value `total`. Version 1 has no such value. The stored prices are only a copy of Alpha Vantage, so `to-v2` removes them and keeps the key and the ETFs. The app then loads the prices again (one request per ETF).
- **Decision:** The section "Rendite" shows the return per calendar year. A year goes from the last weekly close of the year before to the last weekly close of the year. A week over the turn of the year counts to the new year.
- **Decision:** The section also shows the average return per year since the first close of each ETF (compound annual growth rate). The app shows it only with at least 1 year of data. Over a shorter time, a small change gives an absurd value. The option "Mit Ausschüttungen" applies to the whole section.
- **Decision:** The card of a distributing ETF shows its dividends. It shows the sum of the last 12 months per share and the dividend yield (this sum divided by the last close). It also shows the last 4 dividends and the sum per year.
- **Detail:** Alpha Vantage gives the dividend in the week of the ex-date (`7. dividend amount`). Thus the app shows the date of that week, not the payment date. This needs no extra request.
- **Migration (schema version 3, app 3.0):** Each download got the list `dividends`. Like `to-v2`, the migration `to-v3` removes the stored prices and keeps the key and the ETFs.
- **Accepted risk:** The key is in the data file. The data file can be in a cloud folder (OneDrive, Google Drive). The key is free and gives access only to market data, so this risk is small.
- **Rejected:** onvista (no key and good data, but its terms forbid automatic requests). Yahoo, justETF, Börse Frankfurt, EODHD, Stooq (no CORS or bot blocking). The prices of Twelve Data (Xetra needs a paid plan). Marketstack (100 requests per month, 1 year). A GitHub Action that copies prices to GitHub Pages (the terms of the sources forbid publishing them).
- **Size:** About 800 weekly prices per ETF are about 40 KB in the data file. This is no problem.

- **Limit:** The store checks for changes from other devices only before a save. A sync program can change the file between this check and the write. This gap is short, so we accept it.
- **Decision:** The file name comes from the `app` field in `schema.ts`, not from `package.json`. The two are the same (see AGENTS.md), but the schema is the ID of the data.

- **Decision:** In Chromium, the tests replace the folder dialog. It returns a folder in the private file system of the browser (OPFS). Thus the tests use the real File System Access API for reading and writing. Firefox and WebKit test the notice "Bitte Chrome oder Edge verwenden".

## 2026-11-09: CD to Google Drive with rclone and scope drive.file

- **Decision:** `CD - Release` uploads `release/*.html` to a Google Drive folder with rclone. It starts after a successful `CI - E2E` run on `main`. It uploads the artifact of that run, thus exactly the tested files.
- **Decision:** The repository variable `GDRIVE_FOLDER_ID` turns the pipeline on. The secret `GDRIVE_TOKEN` holds the rclone OAuth token.
- **Decision:** The token has the scope `drive.file`. It can only access files that rclone created. If the token leaks, an attacker can change or delete only the app files, not other files in the Drive.
- **Consequence:** rclone must create the folder itself. The folder that the user created before cannot be used.
- **Rejected:** Full Drive scope (a leaked token gives access to the whole Drive). A separate Google account (more setup, the data files in the shared folder are still visible). A service account (no storage quota in a personal Drive).
- **Detail:** The CD job uses only official GitHub actions, pinned to a commit hash.
- **Detail:** `rclone sync --checksum` uploads only files with a changed content. This works because the build is deterministic: the same code gives the same bytes, on macOS and in CI. Thus the date in Drive shows the last real change, and Drive keeps no empty versions.
- **Review fixes:** CD runs only for a push to `main` of this repository (no pull requests, no forks). It uploads only the newest commit of `main`, and only if all five CI pipelines passed for it. It installs a fixed rclone version with a checksum. The setup script stops if the rclone remote has a scope other than `drive.file`.

- **Decision:** The app is one HTML file. The data is a separate JSON file that the user owns. There is no server, no hosting and no browser storage as the source of truth.
- **Why:** Users can share the app file. Updates replace only the app file. Clearing the browser does not delete data.
- **Consequence:** Chrome and Edge save directly into the file (File System Access API). Firefox and Safari save by download. ("Apps on GitHub Pages, data in a local folder" replaces this: only Chrome and Edge, with a data folder.)
- **Consequence:** Phones cannot open a local HTML file reliably. We do not support phones. Layouts must still work in narrow browser windows.
